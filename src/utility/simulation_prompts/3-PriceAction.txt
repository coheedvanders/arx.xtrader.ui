# 1. PURPOSE

The purpose of `priceAction.ts` is to answer:

> **"What is price actually doing right now?"**

This module should interpret the current candle and recent causal price behavior into meaningful price-action events.

It should identify things such as:

* displacement
* rejection
* reclaim
* breakout
* failed breakout
* directional candle pressure
* meaningful price-action sequences

This is **not a prediction engine**.

It should describe and score the quality of what price is currently doing.

# 3. CAUSAL / REALTIME REQUIREMENT

This is critical.

The engine must be completely causal.

At candle `N`, it may only use:

```text

```

It must NEVER use:

```text

```

No future candles.

No look-ahead.

No future-confirmed breakout.

No future-confirmed reversal.

No hindsight classification.

The function must work correctly when processing candles sequentially in realtime.

# 4. WHAT PRICE ACTION MEANS HERE

Price action is not simply:

```text
green candle = bullish
red candle = bearish
```

It should identify **meaningful behavior in context**.

For example:

```text
Price approaches level
        ↓
penetrates level
        ↓
fails to continue
        ↓
closes back away from level
```

is more meaningful than simply saying:

```text
bearish candle
```

Likewise:

```text
compression
    ↓
expansion
    ↓
large directional repricing
    ↓
strong close
```

is meaningful displacement.

The module should therefore combine:

* candle structure
* price movement
* meaningful levels
* recent sequence
* ATR-normalized movement

to determine what price is actually doing.

# 7. DISPLACEMENT

Displacement means:

> **Meaningful directional repricing.**

A large candle alone is NOT necessarily displacement.

For example:

```text
large candle
+
poor close
+
large opposing wick
+
no meaningful movement from previous price
```

should not automatically receive a high displacement score.

A strong displacement should generally have several of:

* expanded range relative to ATR
* strong body
* strong close location
* directional clarity
* meaningful movement away from the prior price area
* continuation from compression
* break through meaningful price structure

Use the existing `CandleStructure` values.

Conceptually, displacement strength can consider:

```text
Range expansion      25%
Body strength        25%
Close location       20%
Directional clarity  15%
Price movement       15%
```

These are starting architectural weights, not absolute requirements.

Make them configurable constants.

```text
Current candle:

bullish candle
price moves significantly upward
```

# 9. REJECTION

Rejection should be interpreted in relation to a meaningful level.

A wick in open space is NOT automatically rejection.

For example:

```text
Price approaches resistance
        ↓
moves above resistance
        ↓
fails to hold above
        ↓
closes back below
```

is meaningful bearish rejection.

Likewise:

```text
Price approaches support
        ↓
moves below support
        ↓
fails to hold below
        ↓
closes back above
```

is meaningful bullish rejection.

Rejection should consider:

* proximity to meaningful level
* penetration of level
* wick behavior
* close back away from level
* failure to continue
* candle structure

The farther the wick occurs from any meaningful level, the less significance it should have.

---

# 10. REJECTION DIRECTION

Use the actual context.

For example:

### Bearish rejection

```text
Price tests resistance
+
upper wick / penetration
+
close below level
```

→ bearish rejection.

### Bullish rejection

```text
Price tests support
+
lower wick / penetration
+
close above level
```

→ bullish rejection.

Do not simply classify:

```text
upper wick = bearish
lower wick = bullish
```

Context matters.

---

# 11. RECLAIM

A reclaim is stronger than simply crossing a level.

A reclaim should require something conceptually like:

```text
price was on one side of a meaningful level
        ↓
price crosses the level
        ↓
candle closes/stabilizes on the other side
```

Examples:

### Bullish reclaim

```text
Price below support
        ↓
moves through support
        ↓
closes above support
```

→ bullish reclaim.

### Bearish reclaim

```text
Price above resistance
        ↓
moves through resistance
        ↓
closes below resistance
```

→ bearish reclaim.

Crossing alone is NOT sufficient.

The engine should distinguish:

```text
wick through level
```

from:

```text
meaningful reclaim
```

# 13. BREAKOUT

A breakout should require more than:

```text

```

A meaningful breakout should consider:

```text

+
close beyond level
+
directional strength
+
preferably displacement / volume confirmation when available
```

The breakout event should identify:

```ts
  strength: number

}
```

If volume data is not yet available in the architecture, do not manufacture it.

Use a neutral/default confirmation value or make it optional according to existing conventions.

# 14. FAILED BREAKOUT

A failed breakout is:

```text
price breaches meaningful level
        ↓
fails to establish beyond it
        ↓
closes back inside the previous range/level
```

For example:

```text
Resistance = 100

High = 102
Close = 99
```

This may represent a failed bullish breakout and therefore bearish price action.

However:

> Do NOT automatically call every failed breakout a liquidity sweep.

A liquidity sweep requires evidence from the Heatmap/liquidity analysis.

So:

```text
Failed breakout
≠
Liquidity sweep
```

Unless a later/other module provides actual liquidity evidence.

# 16. PRICE ACTION SEQUENCE

This is one of the most important parts of the module.

Price action should recognize coherent sequences.

A useful sequence is:

```text
LEVEL / LIQUIDITY
        ↓
SWEEP
        ↓
REJECTION
        ↓
RECLAIM
        ↓
DISPLACEMENT
        ↓
CLOSE CONFIRMATION
```

The complete sequence should be significantly stronger than any isolated event.

For example:

```text
Sweep
+
rejection
+
reclaim
+
displacement
+
strong close
```

is much more meaningful than:

```text
large bullish candle
```

Create something similar to:

```ts
export interface PriceActionSequence {
  liquiditySweep: boolean
  rejection: boolean
  reclaim: boolean
  displacement: boolean
  closeConfirmation: boolean

  completion: number

  direction: SignalDirection
}
```

If actual liquidity-sweep data is not available yet, do not pretend it exists.

Use only the information available at this stage.

---

# 17. SEQUENCE MUST BE NONLINEAR

Do not simply do:

```text
score = sweep + rejection + reclaim + displacement
```

The sequence should have a coherence/confirmation bonus.

For example:

```text
rejection only
```

might be moderate.

```text
rejection + reclaim
```

should be stronger.

```text
rejection + reclaim + displacement
```

should be significantly stronger.

```text
sweep + rejection + reclaim + displacement + close confirmation
```

should represent a high-quality coherent sequence.

The exact mathematical implementation is up to you, but avoid treating every event as an independent vote.

# 18. LONG / SHORT SCORE

Produce directional interpretation:

```ts
long: number
short: number
```

Both should be `0-100`.

These represent:

> How strongly the observed price action currently supports bullish vs bearish interpretation.

They are NOT probability.

They are NOT expected return.

They are NOT a trading recommendation.

They should be derived from actual price-action evidence.

Suggested conceptual weighting:

```text
Displacement       30%
Rejection          20%
Reclaim            30%
Candle structure   20%
```

Breakout/failed-breakout and sequence coherence should modify the appropriate side rather than being blindly added as independent votes.

This is important to avoid double counting.

---

# 19. AVOID DOUBLE COUNTING

For example:

```text
bullish breakout
+
bullish displacement
```

may describe the same underlying event.

Do not give both full independent weight and artificially produce:

```text
100 + 100 = 200
```

Instead, recognize that:

```text
breakout + displacement
```

is a coherent event and should strengthen confidence appropriately.

Likewise:

```text
reclaim + breakout
```

can overlap.

The scoring model should avoid excessive double counting.
